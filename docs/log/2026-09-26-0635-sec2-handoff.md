## What changed, per item

### 1. Per-user daily AI allowance (MEDIUM)

**Migration `0036_ai_quota_and_slipping.sql`, part 1:**
- New table `ai_usage` with the house conventions: `id`, `user_id` (FK to `auth.users`, on delete cascade), `day date` (the Cairo date), `kind` (`'chat' | 'parse' | 'stt'`), `count`, `created_at`, and `updated_at` plus the `set_updated_at` trigger. There is a unique key on `(user_id, day, kind)`.
- RLS: read-own only, through the policy `ai_usage_select_own`. There is no insert/update/delete policy. On top of that, `revoke all` from `anon` and `authenticated`, then `grant select` back to `authenticated`.
- New function `ai_usage_bump(p_user_id uuid, p_kind text) returns int`:
  - It is `security definer` with `set search_path = public, pg_temp`.
  - It is one `insert … on conflict (user_id, day, kind) do update set count = ai_usage.count + 1 returning count`. The day is `(now() at time zone 'Africa/Cairo')::date`, computed in the database, so the edge runtime's clock doesn't matter.
  - Execute is revoked from `public`, `anon` and `authenticated` and granted to `service_role`.
  - Calls past the limit still add to the count, so the row records attempts, not just successes.

**`supabase/functions/_shared/quota.ts` (new):**
- `takeAiAllowance(userId, kind)` calls the RPC on a service-role client, created lazily, with a 5 s abort. It returns `'ok'`, `'over'` or `'unavailable'`.
- `'over'` means the new count is greater than the limit, so the first N calls of the day succeed and call N+1 gets the 429.
- `dailyLimit(kind)` reads `AI_DAILY_LIMIT_CHAT`, `AI_DAILY_LIMIT_PARSE` and `AI_DAILY_LIMIT_STT`. The value must be a whole number ≥ 0; `0` switches that kind off for everyone. A malformed value falls back to the default, never to unlimited, and logs a warning.
- `dailyLimitResponse(req)` returns `429 {"error":"daily_limit"}` with the CORS headers, so the browser can read the body.

**Functions.** All three check the allowance right after `requireUser` and before the request body is read.
- `chat`: over the limit → 429. Check unavailable → `503 {"error":"allowance unavailable"}`, so it **fails closed**.
- `transcribe`: over the limit → 429. Check unavailable → 503, so it **fails closed**. The check also runs before the up-to-20 MB audio upload is read.
- `parse-capture`: over the limit → 429. Check unavailable → it carries on and parses, so it **fails open**.
- Each file has a comment explaining its choice:
  - Parse fails open because a capture must never be lost or degraded by our own bookkeeping. The client already files the capture unparsed if the call fails, so failing closed would only cost the user their AI filing during a blip.
  - Chat fails closed because refusing a question loses nothing, while an unmetered path is exactly what a script would lean on.
  - Transcribe fails closed because speech-to-text has the tightest free-tier budget and the largest calls.
- `search` is not Groq-backed, so it gets no allowance.

**Client** (`features/capture/**`, `features/chat/**` only):
- `features/capture/aiAllowance.ts` holds the one detector for the 429 `daily_limit` answer, through `isDailyLimitResponse(res)` and `isDailyLimitError(err)` (the latter handles `FunctionsHttpError.context`). It also holds `DailyLimitError` and the copy: `AI_ALLOWANCE_USED_UP = "Today's AI allowance is used up — it refills tomorrow."`.
- **Chat:** `streamChat` passes `onError(message, 'daily_limit')`. `ChatPanel` shows the allowance line instead of the "breeze" line.
- **Voice:** `transcribeAudio` throws `DailyLimitError`. `VoiceCaptureSheet` shows the allowance line instead of "Voice capture failed".
- **Parse:** unchanged: the capture lands in the Inbox unparsed. The toast becomes `"Added to Inbox. Today's AI allowance is used up — it refills tomorrow."` instead of `"Added to Inbox for review"`, so it never implies the AI step ran. Any other parse failure keeps the old toast.
- None of the copy contains "error", raw text or status codes, and a unit test asserts that.
- **Unit tests:**
  - `capture/aiAllowance.test.ts`: 9 tests.
  - `capture/api.test.ts`: 7 tests, covering inbox fallback, toast, and `transcribeAudio`.
  - `chat/api.test.ts`: 3 tests.

### 2. Reject anonymous users

In `_shared/auth.ts`, `requireUser` returns `401 {"error":"unauthorized"}` when `getUser(token)` resolves a user with `is_anonymous === true`.
- The flag comes from the user row on the auth server. A converted user, meaning an anonymous user who later links an email, passes.
- This covers `chat`, `transcribe`, `parse-capture`, `search`, and the user branch of `notify`.
- Anonymous users are rejected before the allowance check, so they never touch `ai_usage`.

### 3. notify SSRF (LOW)

**`notify/push-endpoint.ts` (new):** `isKnownPushEndpoint(endpoint)` parses the URL and accepts it only if all of these hold:
- the scheme is `https:`;
- the port is the default;
- there is no username or password;
- the hostname is exactly `fcm.googleapis.com` or `updates.push.services.mozilla.com`, or is one or more DNS labels followed by `.push.apple.com` or `.notify.windows.com`.

The patterns are anchored at both ends. `endpointHost()` is used in logs so a full endpoint, whose path is a per-device token, is never logged.

**`notify/index.ts`:**
- `sendToSubscriptions`, used by both the cron branch and the user `test` branch, filters to allowlisted endpoints first. Anything else is never contacted. It is logged by host and counted as `skipped_endpoints`, both per user and in the top-level total.
- **Semantic change:** `attempted` now counts only the endpoints that were actually tried. `sent` and `pruned` are unchanged, and `notifications/api.ts` still reads those two.

**0036, part 2:**
- The same rule as check constraint `push_subscriptions_endpoint_known_service`:
  ```
  endpoint ~* '^https://(fcm\.googleapis\.com|updates\.push\.services\.mozilla\.com|([a-z0-9]([a-z0-9-]*[a-z0-9])?\.)+push\.apple\.com|([a-z0-9]([a-z0-9-]*[a-z0-9])?\.)+notify\.windows\.com)/'
  ```
- It is added **`NOT VALID`**, so rows stored before 0036 are neither checked nor able to block the migration. `notify` skips them instead.
- Every new insert, and any update of an old row, is checked.
- The match is case-insensitive, as hostnames are.
- The SQL check additionally refuses an explicit `:443` or an endpoint with no path, which browsers never produce. Over the 26 cases in `sec2.sh`, nothing the constraint admits is refused by notify.

## Limits: a decision for Kai

| Kind | Env var | Default (per user, per Cairo day) |
|---|---|---|
| chat (`chat`) | `AI_DAILY_LIMIT_CHAT` | **150** |
| text parse (`parse-capture`) | `AI_DAILY_LIMIT_PARSE` | **300** |
| voice (`transcribe`) | `AI_DAILY_LIMIT_STT` | **60** |

- Nothing needs setting if the defaults are fine.
- The counts are **requests**. One `parse-capture` request can make up to 2 Groq calls, because it retries once when the JSON comes back invalid.
- Calls past the limit still count, but cost nothing but the upsert.
- The day turns over at midnight Cairo time.
- **What this bounds:** one account per day, including throwaway accounts. **What it does not bound:** the total across accounts. Many accounts at their full allowance can still exceed the shared key's free-tier ceiling. The remaining lever is how fast accounts can be created: S10, email confirmation and signup rate limits, which are outside SEC-2.
- I did not check Groq's current free-tier numbers, so the defaults above are the brief's, not derived from them.

## What could break

- **Deploy order.** Functions deployed before 0036 is applied: chat and voice return 503 ("try again") until the migration lands.
- **Kai's own heavy use.** Over 150 chats, 60 voice notes or 300 text captures in a Cairo day now gets the "allowance used up" copy. Captures still land in the Inbox.
- **Voice over the limit loses the recording.** The voice sheet shows the allowance line, but the audio is not saved; there is nowhere to save it without transcription.
- **Fail-open parse.** If the allowance RPC errors or takes more than 5 s, parse runs unmetered. Someone who could deliberately slow the database that much would get free parse calls. I accepted this per the brief.
- **A push service outside the four.** A browser whose push service isn't on the list can't register at all: the insert fails the constraint and the outbox keeps the rejected row visible. Its notifications are also skipped. The four cover Chrome and Chromium browsers (FCM), Firefox, Safari and Edge (WNS), but I did not verify each browser's current host.
- **Response shape.** `notify` responses have one new field, `skipped_endpoints`. `attempted` now excludes skipped endpoints.
- **Shared local DB.** 0036 is now applied there. A worker whose tree lacks `0036_*.sql` and runs `supabase migration up --local` may be told a remote version is missing locally. FIX-5, taking 0037, should branch from or rebase onto this branch.

## What I could not verify

- The real edge runtime and gateway running this code. As in FIX-0, the harness covers the function code, but the shared runtime can't be restarted.
- Groq itself, and real push services (FCM, Mozilla, Apple, WNS).
- Anything hosted, including whether anonymous sign-ins are off there (S10).
- A real anonymous sign-in: it's disabled locally, so I simulated it with the `is_anonymous` flag.
- The 5 s timeout path of the allowance check. Only the error path (invalid key) was exercised.
- Many concurrent calls for one user. This relies on Postgres upsert semantics, not a load test.
- The UI in a browser. The chat, voice and parse copy is covered by unit tests of the API and detector layer. `ChatPanel`'s one-line `reason === 'daily_limit'` switch is not rendered in any test.

## Open questions and out-of-scope notes (one line each, nothing fixed)

- notify's 404/410 pruning never fires: `jsr:@negrel/webpush` 0.5.0 throws `PushMessageError` with the status on `e.response.status`, but notify reads `e.status`, so dead devices are never pruned.
- `webpush` fetches with the default `redirect: 'follow'`, so a push service that redirected would be followed off-list. That would need a library change, and the four hosts are vendor-run.
- `ai_usage` keeps one row per user per kind per day forever. It is tiny, but a retention sweep could ride the compost cron later.
- It would help if Settings showed "12 of 150 today" before users hit the wall. The table is already readable by its owner.
- I left the ROADMAP untouched, since the brief's file list doesn't include it. Its changelog may want a SEC-2 line from the conductor.
- Local leftovers: the test users `sec2-a`, `sec2-b` and `sec2-anon@example.com` remain in `auth.users`, as FIX-0's do. `fix0-a` keeps a few `ai_usage` rows, because each FIX-0 run makes one call of each kind.
