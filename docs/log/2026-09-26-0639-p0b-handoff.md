## Bug 1: offline Journal typing made one entry per keystroke (audit top-10 #2, gap row 4)

**Root cause (confirmed).** The journal list query had never loaded on this device (offline, never opened online), so `data` was `undefined`. `writeRow` skips its optimistic update when there is no cached value (`if (!old) return undefined`). So the row `startFirstEntry` had just created never reached the page. `dayEntries` stayed empty, the blank-day textarea stayed controlled at `''`, and the next keystroke called `startFirstEntry` again with one character. In the real run below, the textarea on screen was still `""` after typing the whole sentence. The same trap affected "+ New entry" and the mood / three-small-things save on an empty day.

**Fix (page side, `JournalPage.tsx` + `journalDay.ts`).** Every journal write on the page goes through `save()` / `hold()`. These keep the page's own latest copy of each row it wrote until the cached list has that row (`holdRow`, `withHeldRows`, both pure and unit-tested). The draft keeps one stable id and its latest body whether or not the list query has data. When the list catches up, the cache wins again. `deleteJournalEntry` and `restoreJournalEntry` now return the row they wrote, so a held row can also be deleted and restored.

**Why `writeRow` does not seed `[row]` into an empty cache.** It isn't safe for every table:
- A seeded list reads as loaded, and fresh for `staleTime` (30s). `writeRow` also cancels the in-flight first fetch, and TanStack then reverts to the seeded state. The page would show one row as if it were everything, e.g. a journal showing only today's entry, or Today flipping from J-10's honest loading state to "1 task".
- `['activity_log']` is shared by two queries with different shapes (Focus: full history ascending; notifications: latest 50 descending).
- `app_settings` is cached as a single row, not a list.

The reasoning is recorded as a comment on `writeRow`. There is no behaviour change in `outbox.ts` for Bug 1.

**Evidence (prod build, local stack, `p0b@example.com`, `docs/log/assets/p0b/journal.mjs`).** Steps: sign in, open `/tasks`, go offline, navigate client-side to `/journal`, type "Written while offline.", reconnect, then count rows via REST.

The same run was repeated on the final build and again gave 1 row. Screenshots: `assets/p0b/b1-before-journal-offline.png`, `assets/p0b/b1-after-journal-offline.png`. At 1280px the Journal layout is still crushed; that is audit item 12, not in scope here.

## Bug 2: signing out offline deleted unsent changes, and the user stayed signed in (audit top-10 #3, gap row 5)

**Root cause.** `signOut()` awaited `flushOutbox()`, which returns immediately offline. It then deleted the outbox and dead letters, and `supabase.auth.signOut()` failed. The queue was gone and the session was still there.

**supabase-js 2.110 behaviour, verified rather than guessed** (`assets/p0b/sbjs-signout.mjs`, node against the local stack, fetch forced to fail):
```
signOut()                   -> error=AuthRetryableFetchError status=0; session still stored; no SIGNED_OUT
signOut({scope:'local'})    -> error=AuthRetryableFetchError;          session still stored; no SIGNED_OUT
remove stored session, then signOut({scope:'local'}) -> no error; session gone; SIGNED_OUT fired
```
So `scope: 'local'` on its own is **not** an offline fallback: it calls the same `/logout` endpoint. The reason is in `GoTrueClient._signOut`: it only removes the session after `admin.signOut` succeeds or returns 401/403/404.

**Fix.**
- `signOut()` (`AuthProvider.tsx`) flushes, then counts what is left (`unsyncedChanges()` in `outbox.ts`). If anything is waiting, it does **not** sign out. It returns the count instead. With an empty queue, or `{ discardUnsynced: true }`, it clears the outbox and dead letters (S7) and ends the session.
- `endSession()`: when online it tries the normal global sign-out, which revokes the session on the server. If that fails, or the device is offline, it removes the stored session and calls `signOut({ scope: 'local' })`. That clears the rest and fires `SIGNED_OUT`, so the existing listener clears the query cache.
- `flushOutbox()` now joins a flush that is already running instead of returning at once. `await flushOutbox()` therefore means the queue has had its turn, and sign-out counts what is really left.
- One flow for every button: `features/auth/useSignOut.tsx` returns `{ request, prompt }`. `AppLayout` uses it for both call sites, the desktop sidebar footer and the phone More sheet (via `MobileTabBar`'s `onSignOut`). There is no Sign out on the Settings page. No other code calls `signOut` or `supabase.auth.signOut`.
- The count doesn't double-count: each action also queues an `activity_log` row, and those are counted only when nothing else is waiting. One capture reads as "1 change".

**Prompt copy for Kai to judge** (`features/auth/signOutCopy.ts`, shown in the existing `ConfirmCard`):
- Title: **"1 change hasn't synced yet"** / **"3 changes haven't synced yet"**
- Body: "It's kept on this device and will sync once you're connected. Signing out now would discard it." (plural: "They're … discard them.")
- Buttons: **"Stay signed in"** (default; Esc and tapping outside also stay) · **"Sign out anyway (discard it / them)"** (terra, destructive)
- The copy contains no "error" and no server text; a unit test checks this.

**Evidence (prod build, local stack, `assets/p0b/signout.mjs`).** Before, on `9996e21` (signOut unchanged): offline, ⌘K capture, 2 entries queued, then Sign out. The user **stayed on `/tasks`, still signed in, queue emptied**. After reconnecting, **0 rows** on the server. The console showed `TypeError: Failed to fetch at signOut`.

After (`2226fb2`, re-run on the final build `92505e4`):

## Scope (3): each outbox entry carries its account

- `OutboxEntry.uid` is the account signed in at queue time. `writeRow` is synchronous, so `outbox.ts` tracks the account from `onAuthStateChange` instead of asking supabase-js at queue time. Writes made in the moment before `INITIAL_SESSION` fires are untagged and follow the legacy rule.
- `flushOutbox()` reads the session with `getSession()` first:
  - **No session:** nothing is sent and the queue is kept.
  - **Session:** only that account's entries go out, plus untagged legacy ones; another account's entries are skipped and left untouched.
- A sign-in kicks the queue, deferred a tick out of the auth event, so held writes go out immediately rather than on the next 30s tick.
- `reapplyPendingWrites` lays only this account's pending writes over its rows.
- `rescueEmptyUserIdWrites`:
  - Tagged dead letters are rescued only for their own account.
  - Untagged legacy ones keep the old rule. Pre-09-24 this was a single-user app, so they are Kai's; the reasoning is in the code comment.
  - Nothing is rescued without a session.
  - Rescued entries are re-queued tagged with the current account.
- **Evidence (`assets/p0b/expired.mjs`).** Queue a capture offline, then expire the session (stored `expires_at` in the past and a dead refresh token), then reconnect and reload.
  - **Before** (`2226fb2`): `/sign-in`, queue 0, **dead letters 2** (401s), 0 rows on the server, even after signing in again.
  - **After** (`4108092`, re-run on `92505e4`): entries tagged with the uid; after expiry, **still queued 2, dead letters 0**; after signing in again the queue drains and the **capture is on the server (1 row)**. The only console line was the expected 400 from the deliberately dead refresh token.

## Scope (4): sign-out drops this device's push subscription

`dropThisDevicePush()` in `features/notifications/api.ts` runs on a real sign-out (empty queue or "Sign out anyway"), before the session ends. It reads this device's subscription, deletes the `push_subscriptions` row by endpoint directly while RLS still allows it (not through the outbox, which sign-out is about to clear), then calls `unsubscribe()`. It is best-effort: it never throws, and each step is time-boxed to 2s. Without the time box, `serviceWorker.ready` never settles when there is no service worker (dev server) and sign-out would hang. "Stay signed in" keeps notifications.

**Evidence:** unit tests only for the delete and unsubscribe. This headless Chromium has no push subscription: there is no VAPID key locally and the push service is unreachable. The real runs above, on `92505e4`, show sign-out still completes online and offline.

## Open questions for Kai / the conductor
1. **Prompt look.** In the 300px `ConfirmCard`, both button labels wrap onto two lines ("Stay / signed in"). It's functional, but you may want shorter labels or a wrapping button row. I left the shared `ConfirmCard` untouched.
2. **Dead letters still go on sign-out without a prompt.** The prompt counts only the live queue. Dead letters are writes the server already refused, and each was announced with a toast when it failed; S7 deletes them on sign-out. Should they count too?
3. **Offline sign-out doesn't revoke the server session.** That isn't possible offline. The device no longer holds the tokens, but the refresh token stays valid on the server.
4. **Offline "Sign out anyway" can't delete the push row.** If `unsubscribe()` also fails offline, the server keeps pushing to this endpoint until `notify` prunes it.
5. **S7 owner check.** It still deletes another account's queue when a different account signs in. With `uid` tags that could later become "keep, don't flush", which would be a product/security call.
6. **Related, not touched:** the topbar sync count still doubles each action (audit #20).
