**Changed:**

It is now async, and it asks the auth server (`GET /auth/v1/admin/users?per_page=1`) to accept the token as an admin. The reason: Supabase's newer API-key docs tell people to turn `verify_jwt` off. If that ever happened, a forged unsigned `{"role":"service_role"}` token would have been accepted by notify and embed. Path 1 is unchanged: a constant-time exact match on `SUPABASE_SERVICE_ROLE_KEY`, with no network call. That is the normal cron case. When path 2 accepts a token, it logs one warning line, because that means Vault's key has drifted from the runtime key.
- notify, user callers: any kind other than `test` returns 403. This includes unknown kinds, and the check runs before kind validation.
- notify, service-role path: each user now has their own try/catch, so one user's failure no longer aborts the run for everyone.
- notify: a failed VAPID import is no longer cached for the life of the worker.

## Per finding

- **S3** (`transcribe`, `parse-capture`, `chat`, `search`)
  - `requireUser(req)` is the first thing after the OPTIONS check, before the body is read or Groq or the DB is touched.
  - It resolves the user with `auth.getUser(token)` on an anon-key client. That call is verified by the auth server, so it works with ES256 tokens. The local user tokens are `alg=ES256`, as shown in the test output below.
  - No token, the anon key, the service-role key, a forged token, or a revoked session gets `401 {"error":"unauthorized"}`. If the auth server is unreachable the function returns 503.
  - `chat` and `search` still forward the user's own JWT, so RLS applies.
- **S1** (`notify`)
  - **Service-role caller:** the function reads `push_subscriptions` once and groups them by `user_id`. It then builds each user's payload with `.eq('user_id', uid)` on every query, including `task_reminder`'s `reminder_sent` update and its `activity_log` insert. Each payload goes only to that user's subscriptions, and there is an extra `sub.user_id === uid` filter as defence in depth.
  - **Response:** `{sent, pruned, skipped, users:[{user_id, skipped, attempted, sent, pruned}]}`. It holds counts only, never content, because pg_net stores responses.
  - **User caller:** only `test` is allowed, and only to the caller's own subscriptions, read under the caller's JWT (RLS). Anything else gets 403. No token or the anon key gets 401.
  - **Wording:** the payload templates are identical to `d14962f`. I diffed all six title/body templates and they match exactly.
  - **Slipping:** the service role sees every user's rows in the `slipping` view. Each user now counts only the domains, projects and areas they own.
- **S5** (`embed`)
  - `isServiceRole` or 401. Users, the anon key, no token and forged tokens all get 401. The drain and backfill logic is unchanged.
- **S9** (CORS)
  - `_shared/cors.ts` reflects `Origin` only if it is on the allowlist. The allowlist is:
    - the production origin;
    - `http://localhost:*` and `http://127.0.0.1:*`;
    - `tauri://localhost`, `http://tauri.localhost` and `https://tauri.localhost`;
    - the comma-separated `ALLOWED_ORIGINS` secret, matched exactly.
  - Every response carries `Vary: Origin`. All inline `'*'` copies are gone, including the one that was in `retrieval.ts`.
- **S4** (`0035_security_scoping.sql`)
  - `do_resurface()` loops over `auth.users` in `created_at` order.
  - Each pick draws only from that user's `tasks` and `inbox_items` (`user_id = v_user_id` on both). The 14-day exclusion and the `review_later` boost check only that user's `resurfaced_log`.
  - **Beyond the brief:**
    - The `activity_log` recency subquery is also filtered to that user. Otherwise another account could log a row against your entity id and lower its weight. This is the same bug class as S4.
    - The insert uses `on conflict (user_id, shown_on) do nothing`, so one user's same-day race can't roll back everyone's pick.
  - Still `security definer` with `set search_path = public`. The 0034 revoke is restated at the end.
  - Kai ruled K-f = yes.
- **S6**: `search_hybrid` keeps the same signature and stays `security invoker`. The body is identical to 0031 except for `<alias>.user_id = auth.uid()` on all 8 branches (verified by diff).
- **config.toml**: `[functions.<name>] verify_jwt = true` for all six. The CLI parses the file (`supabase status` exits 0).
- **DATA_MODEL.md**: one line under `resurfaced_log`.

## How it was verified, and a deviation from the brief

- **Why I didn't use `supabase functions serve`:** it replaces the shared `supabase_edge_runtime_kais-flow` container. The auto-mode classifier denied stopping or renaming that container because it would interfere with the other workers, and it also blocked inspecting it in order to clone it.
- **What I did instead:** `supabase/tests/fix0-auth.sh --harness` serves the six functions under plain Deno 2.9.6 on 127.0.0.1:54390/54391. It uses the real local auth server, PostgREST and DB, with no Docker changes.
- **What the harness does not reproduce:**
  1. There is no gateway `verify_jwt` in front. Every 401 in the output comes from the function code itself, which is the layer FIX-0 adds. I probed the gateway separately against the shared runtime:
     - no token → `401 UNAUTHORIZED_NO_AUTH_HEADER`;
     - forged unsigned `service_role` token → `401 UNAUTHORIZED_UNSUPPORTED_TOKEN_ALGORITHM`.
  2. There is no `Supabase.ai`. The harness stubs a fixed vector, so `search` and `chat` reach `search_hybrid`. The FTS branch returns the rows; the vector branch matches nothing.
  3. Outbound access to `api.groq.com` is blocked, so Groq calls fail after the gate:
     - chat and transcribe return 400 `NotCapable`;
     - parse-capture returns its built-in fallback parse with a 200.

     This is expected. There is no Groq key locally.
  4. `embed` runs against an unreachable DB URL. Its service-role `200 {"embedded":0,"remaining":0}` proves the gate, not a drain. A real drain would have written to 15 queue rows belonging to other workers' test users in the shared DB. The drain code is unchanged from before FIX-0.
- **Push delivery:** a mock push service generates real P-256 subscription keys, decrypts every RFC 8291 `aes128gcm` push, and logs which device received what. The payloads below are what each device actually decrypted.
- **Cron transport:** the local Vault has no `service_role_key`, and the cron URLs are hardcoded to production. So I sent the same `Authorization: Bearer <service_role_key>` header that pg_net sends, using curl.
- **Migration:** `supabase migration up --local` applied only `0035_security_scoping.sql`, cleanly. I dry-ran it in a rolled-back transaction first. The live attributes afterwards:
  - `do_resurface`: `prosecdef=t`, `proconfig={search_path=public}`, EXECUTE only for `postgres` and `service_role`.
  - `search_hybrid`: `prosecdef=f`.

## What could break

- **Cron is the #1 risk.** notify and embed now require the service-role key. Path 1 needs Vault's key to equal the runtime's `SUPABASE_SERVICE_ROLE_KEY` exactly. Path 2 accepts any other valid service_role JWT that the auth server accepts. A `sb_secret_…` value in Vault fails both, because it is not a JWT. Step 6's `net._http_response` check catches this within 5 minutes.
- **Origins.**
  - Tauri v2 is covered: `tauri://localhost` on macOS/iOS/Linux, and `http://tauri.localhost` on Windows/Android (or `https://` with `useHttpsScheme`).
  - Not covered without `ALLOWED_ORIGINS`: Capacitor, a custom domain, and Cloudflare preview/versioned URLs. Of those, only Capacitor is in the plans.
  - A blocked origin shows up as a CORS error in the browser. Server-to-server callers such as pg_net are not affected.
- **Latency and outages:** every user call now makes one auth-server round trip, typically tens of milliseconds. If the auth server is down, the functions return 503 instead of proceeding.
- **Error wording:** a signed-in user calling notify with a kind other than `test` gets 403. Nothing in the app does this.
- **pg_net responses** now store per-user UUIDs and counts. There is no content in them.
- **Legacy API keys:** if they are ever disabled in the dashboard, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` change meaning, and `_shared/auth.ts` needs revisiting. The function modules also now create an anon-key client at load time.
- **Resurfacing** now changes which item surfaces (K-f accepted). Every account gets a pick, and Kai's account only ever sees its own items.

## Open questions and out-of-scope notes (one line each, nothing fixed)

- `do_resurface()` still ignores `deleted_at`, which it has done since 0023, so a trashed row can be picked and the card then shows nothing. Should 0035 or a later migration add `deleted_at is null`?
- `push_subscriptions.endpoint` is globally unique and sign-out doesn't unsubscribe the device. On a shared browser, the previous account keeps receiving pushes, and the new account can't register that device.
- Under the service role, notify's slipping count reads `activity_log` without a user filter, so another account's row logged against your domain id counts as a "touch". This is the same class as the `activity_log` line 0035 fixed for resurfacing.
- The local cron jobs (0006/0007/0009/0016) hardcode the production functions URL. A local stack posts to production with a null Authorization header.
- `grouping.test.ts` fails under `TZ=UTC` since `d14962f`, as described in App checks.
- Signup is open and email confirmation is off (S10), so `requireUser` proves only that the caller has an account. Groq rate limiting (`V1-FEATURES.md:137`) is still the real quota guard.
