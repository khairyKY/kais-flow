## Item 1 — FIX-5 / J-7: `search_hybrid` finds the obvious thing

### What J-7 is, mechanically

`search_hybrid` fuses two arms with reciprocal-rank fusion (RRF), and before this change it gave them **equal weight**:
- vector rank 1 scored 1/61, exactly the same as FTS rank 1;
- the vector arm could fill all **40** of its slots;
- a short query's embedding is close to much of a small corpus, so those 40 slots filled with loose neighbours.

Two more things made it worse:
- A row captured seconds ago has **no embedding yet**, because `embed_queue` drains every 5 minutes. It can only win on FTS, and on FTS it merely tied with the loose neighbours.
- A half-typed word such as `jud` matched **nothing lexically**, because `judg` is a stem and `jud` is not. Only vector noise came back.

### The threshold (please read)

pgvector's `<=>` is cosine **distance** = 1 − cosine similarity.

| Where | Gate as written | Distance | Similarity |
|---|---|---|---|
| `0008` | `< 0.6` | < 0.60 | > 0.40 |
| `0026` / `0031` / `0035` (live before this) | `< 0.45` | < 0.45 | > 0.55 |
| J-7 / FIX-PLAN target | "tighten … 0.6 → ~0.35" | | |
| **`0037` (this)** | **`< 0.35`** | **< 0.35** | **> 0.65** |

J-7 and FIX-PLAN wrote "0.6 → ~0.35" against 0008's `< 0.6`, which is a distance, and both call it a *tightening*. So the ~0.35 is a distance too.

The brief read it as a similarity of 0.35 and called the change a loosening. Under that reading the gate would be distance < 0.65: looser than today's 0.45, and looser even than the 0.6 that J-7 names as the cause. So I didn't use it.

If Kai does want the looser gate, change both `< 0.35` in 0037 to `< 0.65`. The FTS weighting and the 12-row cap still keep vector-only rows below every FTS and title hit either way.

### What 0037 changes (and what it doesn't)

Kept exactly:
- the signature, `security invoker` and `stable`;
- the ACL. It still reads `{=X/postgres,…,anon=X,authenticated=X,service_role=X}`, the same as before.
- the FTS arm, which is 0035's verbatim;
- `user_id = auth.uid()` on every branch. There are now 14 of them: the original 8, plus 6 on the new lexical branch.

Changed:
1. **Vector gate:** distance `< 0.45` → `< 0.35`.
2. **Vector arm cap:** `limit 40` → `limit 12`.
3. **FTS weighted above vector:** FTS `1.0/(60+rank)`, vector `0.5/(60+rank)`. The FTS arm keeps its cap of 40, so its weakest hit scores 1/100 = 0.0100, and the best vector-only hit scores 0.5/61 ≈ 0.0082. **Every FTS hit therefore outranks every vector-only hit.** A row found by both arms still gets both scores.
4. **Lexical guarantee for 1–2 word queries.** A new `lq` / `lex_raw` / `lex_hits` branch:
   - A row qualifies when every query word is an `ILIKE` substring of the row's **returned title**. The query's `\ % _` are escaped, using `E''` strings so the escaping does not depend on `standard_conforming_strings`.
   - "Returned title" means: task title, person name, event title, project name, and the first 80 characters of an inbox item's `raw_text` or a journal entry's `body`.
   - Each qualifying row gets a tier on top of its RRF score:
     - **3**: the title *is* the query (case-insensitive, trimmed).
     - **2**: the phrase starts the title or a word in it (`jud` → "Judge", "Call the judge…").
     - **1**: every word appears somewhere ("prejudged"; two words out of order).
   - RRF sums stay below 0.03, so the tiers decide the order and RRF orders rows within a tier.
   - Queries of 3 or more words switch the lexical branch off. Chat's full-sentence retrieval is therefore unaffected by it.
   - Ties now go to the shorter title, then `entity_id`. Before, ties had no defined order.

### The test: `supabase/tests/fix5-search.sh`

It is psql only. Everything runs in **one transaction that is rolled back**, so nothing is left on the shared stack and no other session ever sees the rows.
- **Accounts:** two throwaway `auth.users` rows. Afterwards `select count(*) from auth.users where email like 'fix5-%'` returns 0.
- **Seed:** each user gets tasks, inbox items, people and journal entries.
- **Embeddings:** synthetic `vector(384)` values. The query vector is e1 = [1,0,…,0], the same one the harness's Supabase.ai stub returns. A row meant to sit at distance d gets `[1−d, 0,…, √(1−(1−d)²), …]`, so `<=>` returns exactly d.
- **Calls:**
  - as role `authenticated` with `request.jwt.claims` set, the way PostgREST calls it;
  - again as the superuser with the same claims, where RLS does not apply. This exercises the function's own per-branch predicates.
- **Classification:** each returned row is classified independently of the function:
  - **F**: its text matches the tsquery;
  - **L**: every query word is a substring of its title;
  - **V**: its embedding is within 0.35;
  - "vector-only" means neither F nor L.
- **Flags:**
  - `--show` prints every ranking checked.
  - `--with <file>` applies a migration inside the same rolled-back transaction first. That is how the full dry run was done.

The seed follows J-7 literally:
- A's `Judge` task has **no embedding**: it was just captured.
- 16 "rigorous ejection modal NN" tasks and 4 inbox items sit at distance 0.11–0.26, with no words in common with the query.
- 3 rows sit at 0.40–0.42, inside 0.45 but outside 0.35.
- Three trashed rows are seeded. Two of them sit at distance 0.02–0.03, so they would be the top vector hits if the `deleted_at` guard were missing.
- User B has a strong match for every query, including an exact `Judge` at distance 0.01.

## Item 2 — notify never pruned dead push devices

**Verified against the library source**, not guessed. The Deno cache holds `https://jsr.io/@negrel/webpush/0.5.0/subscriber.ts`.
- `0.5.0` is the package's `latest` in the cached `meta.json`.
- `mod.ts` re-exports `./subscriber.ts`, so `webpush.PushMessageError` is public.
- `pushMessage` ends with `if (!response.ok) { throw new PushMessageError(response); }`, and:

```ts
export class PushMessageError extends Error {
  public readonly response: Response;
  constructor(response: Response) { super(); this.response = response; }
  isGone(): boolean { return this.response.status === 410; }
  …
}
```

There is no `.status` on the error. `(e as { status?: number })?.status` was therefore always `undefined`, and the 404/410 branch was dead code.

**Fix** (`supabase/functions/notify/index.ts`, `sendToSubscriptions`):
- `const status = e instanceof webpush.PushMessageError ? e.response.status : undefined`.
- 404 or 410 → `delete … .eq('id', sub.id).eq('user_id', userId)`. That is the same per-user scoping as before (FIX-0). The subscriptions reaching this point were already filtered to `sub.user_id === userId`.
- `pruned` now counts only deletes that succeeded. A failed delete is logged by host, never by full endpoint.
- Any other failure, including a 500, never prunes.
- I did not use `isGone()`: it covers only 410, and a 404 also means the subscription is gone.

**Harness** (`supabase/tests/harness/mock-push.mjs`):
- The mock push service answers every push with 201, unless `MOCK_PUSH_STATUS` names a JSON file mapping device → HTTP status. The file is re-read on every request, so a test can change the answers between calls.
- The status sent is logged with each push. Existing callers set nothing, so they get exactly the old behaviour; fix0 and sec2 still pass.

**New `supabase/tests/notify-prune.sh`:**
- It runs in harness mode with its own accounts, `notify-prune-a@`/`-b@example.com`.
- A has devices `np-a1..3`; B has `np-b1..2`. All endpoints are on allowlisted push hosts.
- "Nothing else deleted" is checked against a snapshot of the **whole** `push_subscriptions` table, not just the test users' rows.
- `FN_DIR` lets the same script serve a different functions directory. I used it to run the checks against the pre-fix `notify`.

## What could break or change behaviour

- **Chat retrieval shrinks.** `chat` calls the same function with the user's whole question, so the lexical branch is off there. Its vector context is now at most 12 rows within distance 0.35, where before it was up to 20 rows within 0.45. A question sharing no words with the data and only loosely related to it can now get less context, and more often "That's not in your data". This is the intended trade-off of J-7; it applies to chat as well.
- **The vector gate is untested against real gte-small embeddings.** I tested with synthetic vectors, because the embedder doesn't run locally. Where real "related" pairs actually fall relative to 0.35 is unmeasured; see the open questions.
- **Title hits outrank body and notes hits for 1–2 word queries.** For `judge`, "prejudged ideas list" (tier 1, substring inside a word) ranks above a task whose *notes* say "judge" and above a person whose *facts* do. Both of those still appear, right after the title hits. That follows from "literally in a title always ranks". If Kai would rather have whole-word notes and facts hits beat partial-word titles, the fix is to give tier 1 a smaller bonus.
- **Single-character queries** return every title containing that character, shortest first, up to the limit. That is harmless for search-as-you-type, but it is a change: before, they returned only vector noise.
- **Websearch syntax is literal in the lexical branch.** A query in quotes (`"judge"`) or with a leading `-` gets no lexical boost. FTS still handles those as before.
- **Cost:** see the Cost section above, roughly +20–50 ms per call on a 6,800-row account.
- **notify:** `pruned` in the responses can now be non-zero.
  - Settings' "send test" shows `Sent to N device(s), pruned M dead subscription(s).` (`SettingsPage.tsx:417`), and M can now be more than 0.
  - A device the push service reports gone is deleted during that test.
  - This is intended, and Kai will see it.

## What I could not verify

- Real gte-small embeddings, and the edge runtime's `Supabase.ai`, against the new threshold. All vector evidence is synthetic.
- The deployed `search` / `chat` path end to end against 0037. The harness `search` call in fix0 does reach the live 0037 function through PostgREST, and it passes.
- Real push services' 404/410 behaviour. The mock returns those codes; the library code path and the prune were exercised against the mock, not FCM, Mozilla, Apple or WNS.
- Hosted performance on Kai's real corpus size. The timings above are local and synthetic.

## Open questions (one line each)

- **Threshold reading:** is 0.35 meant as a distance (applied; tighter) or a similarity (distance 0.65; looser)? Deciding needs a real query log or a few known good and bad pairs measured with the actual embedder.
- **Pin the library:** `jsr:@negrel/webpush` is still unversioned in `notify/index.ts`. The fix is verified against 0.5.0, and pinning `@^0.5.0` (as `harness/vapid.ts` already does) would lock that in.
- **Tier-1 order:** should partial-word title matches ("prejudged") rank below whole-word notes and facts matches? See the behaviour change above.
- **ROADMAP:** I left it untouched, because the brief's file list doesn't include it; its changelog may want a FIX-5 line from the conductor.
- **Local leftovers:** `notify-prune-a@` and `notify-prune-b@example.com` remain in `auth.users`, as the fix0 and sec2 accounts do; their push rows are removed at the end of each run. `fix5-search.sh` leaves nothing, since everything is rolled back.
