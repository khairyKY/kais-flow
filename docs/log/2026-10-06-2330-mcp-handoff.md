# MCP server — handoff (builder M, branch `claude/mcp`)

AI assistants (Claude Code, Claude Desktop, any MCP client) can now read a user's Kai's Flow and, with
a read & write key, add to it. User docs: `docs/MCP.md`. Started from `origin/master` (v1.0.20), merged
`origin/claude/wave-r` before the final gate.

## Protocol choice

The current spec is **2026-07-28**, which made MCP stateless: no `initialize`, every request carries
`_meta` (protocol version + client capabilities) and mirrors method / tool name / version into the
`Mcp-Method` / `Mcp-Name` / `MCP-Protocol-Version` headers. Most clients in use still speak the
2025-xx revisions (open with `initialize`). So the server is **dual-era**, which the spec allows:

- `initialize` → legacy: echoes 2025-11-25 / 2025-06-18 / 2025-03-26 (else offers 2025-11-25); no
  `Mcp-Session-Id` (sessions are optional in those revisions), GET/DELETE → 405, notifications → 202.
- A request with modern `_meta` → validated per 2026-07-28 (400 `-32020` header mismatch incl. base64
  `Mcp-Name`, 400 `-32022` unsupported version with `supported`, 400 `-32602` missing `_meta`, 404
  `-32601` unknown method), results carry `resultType: "complete"` + `_meta` serverInfo;
  `server/discover` implemented.
- Tools only (resources weren't cheap enough to be worth it: every tool already returns text the model
  reads). One `application/json` reply per POST; no SSE, no batches. `Origin` checked (403) with the
  app's own allowlist (`_shared/cors.ts`).

## Auth choice — and running as the user

- **A personal key, not OAuth.** Supabase Auth's OAuth 2.1 server would need a consent page in the app,
  dynamic client registration and dashboard setup [KAI] — not small. The key is the capture key's model
  (0041): per user, SHA-256 at rest, revocable, plus a read-only scope. Claude Code (`--header`) and
  Claude Desktop (via `mcp-remote`) take it today; claude.ai's "Request headers" connector field is an
  Anthropic beta. Upgrade path written in `docs/MCP.md`.
- **No service role for user data.** A key holder has no Supabase session and functions get no JWT
  signing secret, so a user token can't be forwarded or minted. `index.ts` opens one Postgres
  transaction per request on `SUPABASE_DB_URL` (a default function secret): it looks the key up and
  bumps the counter as the table owner, then `set_config('role','authenticated', true)` +
  `request.jwt.claims = {sub: <owner>}` — what PostgREST does — and **checks `current_user` and
  `auth.uid()` before any tool runs** (throws otherwise). Every tool query is then under RLS.
- Rate limit: 500 tool calls per key per UTC day (only `tools/call` counts; over it, a readable tool
  error). Key format checked before the database is touched.

## Tools

`today` (Top 3 / due or scheduled today / overdue / today's events, on `app_settings.timezone`, Cairo
when unset or unknown — own helper in `tools.ts`, independent of the in-flight TZ work), `search`
(`_shared/retrieval.ts`'s embedding + `search_hybrid`; **journal entries and people are dropped**),
`list_tasks` (status, project, label, due range → user-day bounds, limit), `get_task`, `add_task`
(title, due — a bare date = 09:00 local, project → its domain, top3 ≤ 3 open, notes), `complete_task`
(a repeat's next occurrence planned before any write, `npm:rrule` like the app, reminder lead kept,
no duplicate if one is open), `move_to_tomorrow` (tomorrow 09:00 local), `add_to_inbox` (pending text
item, link appended, like the capture endpoint), `calendar` (inclusive days, default today+6, ≤ 31),
`projects`. Every write logs the app's activity event (`task.created` / `task.starred` /
`task.completed` / `task.rescheduled` / `inbox.captured`) with `source: 'mcp'`. Bad arguments
(including unknown argument names) come back as `isError` tool results in plain words; database errors
as a detail-free one.

## Risks and deviations

- **The SQL in `index.ts` has never run** (no Deno, no database on this machine). It's type-checked and
  uses only plain statements with explicit casts; the role switch is verified at runtime before any
  tool runs. If `SUPABASE_DB_URL`'s user could not `set role authenticated`, every call returns 500 —
  safe, but the feature would be dead until fixed. The local stack's own tests
  (`supabase/tests/fix5-search.sh`) use the same switch as `postgres`.
- **Migration number 0050**: the parallel time-zone builder may also add one; rename on merge if so.
- **The brief's "mocked Supabase client"** became a mocked `Store`: the data path is SQL on the
  database connection (to run under RLS without a JWT), not supabase-js, so the Store is the seam.
- **Journal entries and people are excluded** from `search` (CLAUDE.md privacy rule: journal content
  goes to Groq only). `docs/MCP.md` says so, and the card says "your journal and people are never shared".
- **Not done (said in docs):** OAuth; resources/prompts; labels / reminders / scheduling blocks in
  `add_task`; one key per user (like the capture key), so separate keys per assistant aren't possible.
- `supabase/config.toml` was touched (one `[functions.mcp]` block) — required: the gateway would
  reject a `kf_ai_` key as a bad JWT otherwise.
- The card's dates read `app_settings.timezone`; if the TZ work adds a shared zone hook, `McpCard`'s
  `day()` can switch to it.
- `app/node_modules` was installed in this worktree with `npm ci` (lockfile identical to the main
  checkout) to run the gate; it's gitignored and left for re-runs. `dist/` and `.env.mock.local` removed.
