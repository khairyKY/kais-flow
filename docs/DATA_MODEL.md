# Kai's Flow — Data Model Reference

> Consolidated schema. Each table notes the phase that introduces it. **Update this file whenever a migration lands.** Sketches here are the contract; exact SQL lives in `supabase/migrations/`.

## Universal conventions (every table)

- `id uuid primary key` — generated **client-side** (`crypto.randomUUID()`) so offline writes are idempotent upserts.
- `user_id uuid not null default auth.uid()` + RLS policy `user_id = auth.uid()` for all of select/insert/update/delete.
- `created_at timestamptz default now()` · `updated_at timestamptz default now()` bumped by the shared `set_updated_at()` trigger. *(2026-10-12)* Three tables have **no `updated_at`** (no column, no trigger): `push_subscriptions` and `routine_completions` (0005 — rows are inserted and deleted, never edited) and `resurfaced_log` (0008 — its `action` / `snoozed_until` are updated in place without a timestamp).
- All timestamps stored UTC; rendered — and every "what day is it" decided — in the user's own `app_settings.timezone` (Africa/Cairo by default; user time zones, 2026-10-04: `app/src/lib/appZone.ts` on the client, `supabase/functions/_shared/zone.ts` on the server — its `dateKey` / `dayWindow` / `wallToInstant` are the server's one day math since 2026-10-12, shared by notify, chat and mcp). ~~The one exception is the AI allowance's day (`ai_usage`), which is Cairo's for everyone.~~ *(2026-10-12, corrected:)* The exceptions: the AI allowance's day (`ai_usage`, `ai_usage_global`) is **Cairo's** for everyone (one shared Groq budget), and two days are **UTC**: resurfacing's once-a-day pick (`resurfaced_log.shown_on = current_date` in `do_resurface()`) and an AI access key's daily call count (`mcp_keys.calls_day = current_date`, 500/day).
- Realtime: tables the UI subscribes to must be added to the `supabase_realtime` publication.
- **Soft delete (0023):** `deleted_at timestamptz?` on `tasks`, `inbox_items`, `calendar_events`, `journal_entries` (partial index `where deleted_at is not null`) — these four are what the Trash page lists. **Compost (0032, V1 punch 25):** `compost_expired()` (`security definer`, `execute` revoked from `public`/`anon`/`authenticated` so only the cron owner can call it) hard-deletes those rows 30 days past `deleted_at`, plus `inbox_items` left `status = 'dismissed'` 30 days past `updated_at`. pg_cron job `compost-expired`, daily 03:30 UTC; returns the row count so it can be verified by hand.
- **Projects + areas in Trash (0044, Kai 2026-10-03):** `deleted_at timestamptz?` on `projects` and `areas` (same partial indexes). Delete (Projects page ⋯ / right-click) = Trash + "Moved to Trash · Undo", no confirm; `useProjects`/`useAreas` hide trashed rows; Trash lists and restores them. Their tasks are not touched: a task keeps its `project_id`/`area_id` while the container rests in Trash, so Undo/Restore puts everything back. `compost_expired()` now also hard-deletes `projects`/`areas` 30 days past `deleted_at` (after `tasks`), and the FKs release the remaining tasks — `tasks.area_id` became `on delete set null` here (0010 had no action, which would have failed the compost), matching `tasks.project_id` (0002). `time_entries.project_id` stays `on delete cascade` (0020): a composted project's logged hours go with it. The `slipping` view skips trashed projects/areas.
- **One container per task (0052, Kai 2026-10-06):** a task lives in a project **or** an area, never both. Every move into a project (`setProject` — the ⋯ / right-click / swipe / `p` / task sheet / bulk "Move to project…") clears `area_id`, and drops `milestone_id` when the project changes; "No project" leaves an area task in its area. ~~0050~~ 0052 *(2026-10-12: the repair is 0052's; 0050 is user time zones)* is a one-off repair (`area_id = null` where both were set — the project was the later choice); no check constraint, so an older build's queued offline write can't get parked.
- **Top 3 order + the goal of the day (0055, Kai 2026-10-07):** `tasks.top3_rank smallint?` is a pick's place in Today's Top 3, 1 = the goal (the first pick is the goal, SCREENS-2026-09-28 §Plan ruling 4). It replaces the goal's device-local localStorage pick (`kf_goal_task_id`, now read only as the fallback while none of the day's picks has a place), so the phone and the computer agree. Today orders its Top 3 by rank, the unranked after them in Today's own order (`features/today/top3Order.ts`); a rank is read only while the task is in the day's Top 3, so a stale rank on an unstarred row (an old build doesn't clear it) is harmless. Writes: Make goal of the day (⋯ / right-click / task sheet ⋯ / Plan my day) and Move up / Move down, Alt+↑/↓ and the desktop drag renumber the day's picks 1…n (only changed rows are written); a star joins with no rank (last), an unstar clears it; completing keeps it, so a finished goal stays the goal (R4); a spawned repeat or a duplicate starts unranked. Plan my day's Start the day ranks the picks in pick order. The cap of 3 stays client-side (no check constraint, no unique index — the 0052 reason, and two devices renumbering at once must not reject each other). `activity_log` gains `task.goal_set` and `task.top3_moved` (payload `{rank}`); Make goal into a full Top 3 also logs the `task.unstarred` / `task.starred` the swap makes. `app_settings.weekend_days` is the user's weekend (below). **Replan:** where a replanned task's blocks go is calendar-rail's rule (`features/calendar/replan.ts`, through `rescheduleDue` — every due change: the Plan menu, swipe, the 1/2/3 keys, bulk, rituals): a time puts it on the calendar at that time (its block moves, else a new one); a date alone keeps a block already on that day and takes any other off; no date takes them all off; a missed due date follows a block placed today or later. The Plan menu passes the date picker's `timed`; Next free slot's Confirm and Spread into free slots are timed replans; `rescheduleDue` returns the exact Undo.
- **Domains in Trash (0053, Kai 2026-10-06):** `domains.deleted_at timestamptz?` (partial index), the 0044 pattern. Domains are managed in Settings → Organize and on the Tasks page's Organize card (create · rename in place · recolour · merge · delete). Delete = Trash + "Moved to Trash · Undo", no confirm; `useDomains` hides trashed rows (parse-capture's context too); Trash lists and restores them. What's in a trashed domain is not touched — projects, areas, tasks, people, routines and notes keep `domain_id`, read as "no domain" meanwhile, and come back with Undo / Restore; `compost_expired()` hard-deletes domains 30 days past `deleted_at` (after projects/areas) and the set-null FKs release the rest. Merge (`mergeDomain`) re-points every cached row of those six tables to the chosen domain, then trashes the emptied one — one Undo takes it all back. `activity_log` gains `domain.recolored`, `domain.deleted`, `domain.restored`, `domain.merged` (payload `{into, name, moved}`). The `slipping` view skips trashed domains.
- **Changing a thing's type (Kai 2026-10-06, no migration):** from a project / area row's ⋯ ("Change type…"), its page's footer, or a domain's menu ("Make it an area…"); a one-line confirmation, then one Undo restores every rewritten row and removes the new one (rules + tests: `app/src/features/projects/convert.ts`). project ↔ retainer = flip `projects.type` only (the 0047 reload picks a retainer up on the next 1st). project / retainer → area = a new `areas` row (name, domain, colour); every task in it gets `project_id = null`, `area_id = <new>`, `milestone_id = null`; the project goes to Trash with its milestones, checklist, `time_entries` and status updates (restorable 30 days, then composted — `time_entries` cascade). area → project = a new standard project; its tasks get `project_id`, the area's `domain_id`, no `area_id`; the area to Trash. area → domain = a new `domains` row (name, colour); its tasks get that `domain_id`, no area; the area to Trash. domain → area = a new area (no domain); its loose tasks (no project, no area) move in; its projects, areas, people, routines, notes, and the domain link of tasks inside its projects / areas, go to `domain_id = null`; the domain to Trash. `activity_log`: `<project|area|domain>.type_changed` `{from, to, name, new_id?}` on the source, `<…>.created` `{name, from}` on the new row, `<…>.type_restored` on Undo.
- **Editing a project's status updates (Kai 2026-10-06, no migration):** an update is an `activity_log` row (`project.update_logged` `{note}`), and the log stays append-only — an edit appends `project.update_edited` `{update_id, note}`, a delete `project.update_deleted` `{update_id}`, its Undo `project.update_restored` `{update_id}`, all on the project; the feed resolves them (`app/src/features/projects/statusLog.ts`, tested). Work entries are real `time_entries` rows: edit = upsert `note` (+ `project.work_edited`), delete = hard delete with an Undo that writes the row back (+ `project.work_deleted` / `project.work_restored`, payload `{time_entry_id}`). `logActivity()` now returns the row it wrote.
- **Import idempotency (0027, P-IMPORT):** `external_ref jsonb` (nullable) on `tasks`, `inbox_items`, `journal_entries`, `notes`, `people`, `projects`, `calendar_events` — `{source, id, raw}` — with a partial unique index on `(user_id, external_ref->>'source', external_ref->>'id')`. Re-importing the same file is a no-op; the whole source row survives in `raw`. A task filed from a GitHub inbox item carries `{source:'github', id:<issue node_id>, url}` (the task's "View issue" link, P6 step 4). Duplicates and next occurrences never copy `external_ref` (it is a unique key).
- **Captured links (P7e A19, 2026-10-13 — no migration):** a task made from a capture that carried a link (the bar's typed link, a share's text, the capture endpoint's `payload.url`, an AI-filed voice/typed/queued line) has `external_ref = {source:'link', id:<random uuid>, url}` — `url` is http(s) only (`lib/links.ts`). The id is random so 0027's unique index never collides when the same page is captured twice. The task sheet/editor show it ("example.com ↗", a GitHub one "View issue"); `o` on a task row opens it.

**Extensions:** `vector` (pgvector, P0), `pg_cron` (P0), `pg_net` (P4 — lets cron call edge functions over HTTP).

### P5 — search & chat
- `tsvector` generated columns (`search_tsv`) + `embedding vector(384)` (gte-small) added to `tasks` (title+notes), `inbox_items` (raw_text) — GIN index on `search_tsv`, HNSW (`vector_cosine_ops`) on `embedding`. `search_tsv` is `generated always as (...) stored` — **never include it in a client upsert payload** (`lib/outbox.ts`'s `writeRow` strips it automatically; Postgres 400s if a write tries to set it).
- `embed_queue` — `entity_type`, `entity_id`, `content text`, `status text ('pending'|'done'|'error')`, unique `(entity_type, entity_id)` — filled by insert/update triggers on `tasks`/`inbox_items` (update triggers are WHEN-guarded on the actual searchable columns so the `embed` function's own `embedding`-only writes don't loop), drained by the `embed` edge function (cron every 5 min via pg_net, same Vault-secret pattern as `notify`).
- `search_hybrid(query_text, query_embedding, match_limit)` — SQL function (`security invoker`, so RLS on the underlying tables scopes it per-user automatically): FTS (`websearch_to_tsquery`) + vector (cosine, capped at distance < 0.6 to keep unrelated matches out — tightened to 0.45 in migration 0026) each ranked and capped at 40, merged via Reciprocal Rank Fusion (`1/(60+rank)`), top `match_limit` (default 20) returned.
  - **Migration 0031 (punch 49)** widened the **FTS branch only** to `people` (name + every fact label/value), `calendar_events` (title), `projects` (name + `completion_summary`) and `journal_entries` (body + transcript), and added `deleted_at is null` guards so trashed rows stop matching. Returned `entity_type` values are now `task | inbox_item | person | calendar_event | project | journal_entry` (mirrored by `SearchEntityType` in `lib/types.ts`). Those four tables deliberately have **no** `search_tsv` column and **no** GIN index — `to_tsvector` is computed per row inside the query, which is sub-millisecond on a one-person corpus; add stored columns + indexes (exactly as 0008 does for `tasks`) if it ever gets slow. The **vector branch stays `tasks` + `inbox_items`**: only those two have `embedding` columns and `embed_queue` triggers, so the new types are keyword-only.
  - **Migration 0037 (FIX-5, J-7):** same signature, still `security invoker` with `user_id = auth.uid()` on every branch; vector gate tightened to cosine **distance** `< 0.35` (similarity > 0.65; was `< 0.45`) and the vector arm capped at **12** (was 40); RRF weights FTS `1.0/(60+rank)` over vector `0.5/(60+rank)`, so every FTS hit outranks every vector-only hit; for 1–2 word queries a lexical arm (`ILIKE`, the query's `\ % _` escaped) adds a tier to rows whose returned `title` contains every word — **3** the title equals the query, **2** the phrase starts the title or a word in it, **1** anywhere — so a literal title match always ranks, exact titles first; ties go to the shorter title. Checks: `supabase/tests/fix5-search.sh`.
  - **Migration 0054 (Kai 2026-10-06, "it brought an entry but it wasn't there"):** 0037's body plus two changes — trashed projects (0044 `deleted_at`) are skipped in the FTS and lexical arms (they opened a page that rightly doesn't show them), and **areas** are searched (FTS + lexical; `entity_type 'area'`, title = name, snippet = description, trashed skipped).
