## P0 — the persistence cluster · **ROOT-CAUSED & FIXED**

Four claims, one cause:

| # | Kai's words | Status |
|---|---|---|
| P0-a | "if I dismiss smth it comes back to the inbox" | **DONE** |
| P0-b | "Filing something from the inbox just doesn't work. Like it comes back waiting" | **DONE** |
| P0-c | "I changed the color of one of these projects before, but now they're all the same color and the color… has been reset" | **DONE** |
| P0-d | "every time I refresh the page… it takes me automatically to the onboarding" | **DONE** (see also #25) |

**Two hypotheses were tested and one was eliminated.** A read-only schema probe against the live
database (public anon key only — no credentials) confirmed **every migration is applied**,
including `0028_routine_steps` (`routines.steps`, `routines.domain_id`) and `0029_subtasks`
(`tasks.parent_task_id`). Missing columns were *not* the cause.

**The actual mechanism — a write-behind read race.** `lib/outbox.ts` is a write-behind queue:
`writeRow()` updates the TanStack cache optimistically, then flushes to Supabase asynchronously.
The read path had no knowledge of that queue. `lib/realtime.ts` invalidates a table's query on
**every** change to it (including changes we caused), and any refetch landing between the
optimistic update and a successful flush replaced the cache with server rows that don't carry
the pending change yet — silently reverting the UI. That is exactly "it comes back *right away*",
and it explains all four symptoms at once.

Fixes in [outbox.ts](../app/src/lib/outbox.ts):
1. `reapplyPendingWrites(table)` lays the outstanding queue back over every fresh fetch, so the
   cache reads "server state **+ what we still owe it**". Wired via a single query-cache
   subscription (all tables are keyed by `[table]`), skipping manual writes to avoid a loop.
2. `cancelQueries()` before the optimistic write, closing the narrower in-flight-fetch window.
3. A server **rejection** (PostgrestError shape — expired session, RLS denial) now raises one
   toast per stuck row naming the table and the real message, instead of being swallowed
   identically to being offline. Genuine network failures stay silent as before.

4 regression tests, **verified to fail without the fix** (temporarily neutralised the re-apply;
3 tests went red, then restored).
