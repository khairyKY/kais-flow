## Item-by-item: current state → what to build

1. **View row `1–6 / W / M`** — *mostly exists, presentation differs.* Step 11a (session 14) shipped the always-visible Day · N-day · Week · Month toolbar switcher (`CalendarGrid.tsx:78–86`) plus a separate N `Select` in page chrome (`CalendarPage.tsx:225–227`, options 2–6). Kai's shot shows the Akiflow shape: direct day-count buttons inside one popover. Build: a **calendar view-options popover** (ContextMenu/Select panel language) whose View row is the segmented `1·2·3·4·5·6·W·M`; tapping `n` writes `calendar_day_count` (existing setting, migration `0015`) *and* activates the N-day view (1 = Day). The standalone N `Select` from 11a is then redundant — remove it; the FullCalendar toolbar switcher stays. Lineage: #50/#55.
2. **Density S/M/L** — *new.* Three slot-height presets via CSS on `.fc-timegrid-slot` in `CalendarGrid.css` (FullCalendar sizes the grid off that height); no FullCalendar API needed.
3. **Secondary time zone** — **stays skipped.** Standing ⛔ in the gap analysis ("Cairo-only life", §2.4 + "skipped for good" list). It appears inside Kai's lasso because the whole popover is circled; not treating that as a re-litigation. **Kai: if you actually want a second time zone, say so explicitly and we'll revisit.**
4. **Weekends toggle** — *new, one prop.* FullCalendar's `weekends={false}` hides Sat/Sun columns.
5. **Declined events toggle** — *nothing to hide yet.* Declined-ness only exists on synced Google events; gcal sync is P9. Routed as a one-line note on the P9 row in the gap analysis §2.4 — the popover simply has no such row until then.
6. **Done tasks toggle** — *new, small.* Grid events already know their task linkage (`task_id` on every event; `CalendarPage.tsx:380` maps `linked`). Toggle off → filter out events whose linked task is completed before handing them to `CalendarGrid`.
7. **Board granularity Overview · D · W · M** — *new, the real work of this round.* `planningColumns(tasks, now)` (`grouping.ts:170`) hardcodes the five Overview buckets (today/tomorrow/week/nextWeek/someday) and `applyColumn` (`PlanningBoard.tsx:19–37`) maps a drop to its setter. Build: `planningColumns` gains a granularity mode — **Overview** (as-is) · **D** = next 7 days, one column per day · **W** = this week + the next ~3, one per week · **M** = this month + the next ~2, one per month — each column carrying its own target date so drop/quick-add re-dates via the existing `rescheduleDue` (column start day; week → Monday, month → the 1st, reusing the `dateShortcuts` time-preserving convention once 14a lands). Someday stays a pinned last column in Overview only (judgment call, logged for Kai's override). Unit-test the column generator alongside the existing grouping tests.
8. **Board view-options popover** — *new, same popover component as item 1.* **Compact view** (rows drop the chip line + tighten padding — a `compact` presentation of the shared `TaskRow`, which the board already reuses) · **Show Done** (`planningColumns` currently filters `status === 'todo'` at `grouping.ts:171` — the toggle includes completed tasks, rendered dimmed at column bottom) · **Sort By ▸** (within-column order: due date · priority · duration · title; pure function, unit-tested) · **Filter By Projects ▸** (reuse `ProjectPicker` as the submenu; scope = URL param `/planning?project=<id>`, matching the `?list=` pattern — filters are shareable state, not settings). **Tags ▸ waits for P6 step 5** — `labels` has no UI until then; the popover gains its Tags row in that step (noted there via the gap analysis).
9. **"Tasks not scheduled" tray** — *the concept already exists; the gaps are labeling + reach.* The calendar rail is already unscheduled-only by design (`CalendarPage.tsx:96–98` filters `!t.scheduled_start`) and scope-able (step 8). Build: (a) make the rail say so — header/empty-state copy names it "Not scheduled" so the semantic is visible, per 14b's one-taxonomy rule; (b) the planning board gains the same collapsed **Not scheduled** tray (same filter, cards drag into columns — dropping onto a column dates the task via item 7's mapping). If Kai meant something else by the annotation, say so — this is the reading that matches the arrow's target.

## Persistence — one migration, not eight

The popovers introduce ~7 toggles. `app_settings` has so far grown one typed column per setting (0003→0015), which is right for cron-read values (`digest_hour`, `timezone`) but wrong for a bag of cosmetic view preferences — nothing server-side ever reads these. **Migration `0020_view_prefs`:** `alter table app_settings add column view_prefs jsonb not null default '{}'::jsonb` — every toggle from both popovers lives in that one bag (`calendar_density`, `calendar_weekends`, `calendar_show_done`, `board_granularity`, `board_compact`, `board_show_done`, `board_sort`), typed by one Zod schema per the one-schema-per-entity convention, read/written through the existing `useAppSettings`/`updateAppSetting` path (`writeRow` round-trips jsonb fine — it spreads the row). `calendar_day_count` stays a real column (shipped, two writers already). Future view toggles cost zero migrations. `// ponytail: jsonb bag, promote a key to a real column only if a cron/edge fn ever needs to read it`
