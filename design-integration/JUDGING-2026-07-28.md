## J-1 · 🔴 Desktop rows enter the phone swipe state — the headline

**Symptom (Kai):** "when I try to interact with any task it automatically goes to the state where you drag the task left and right for other actions, this was only intended to be on the phone's version."

**He's right about the intent:** swipe actions are the iPhone variant's gesture (Tasks.dc.html **1b**; drift audit C-12). The desktop design has hover actions and the context menu instead.

**Root cause:** `useRowSwipe()`'s handlers are spread onto `.tr-swipe-content` **unconditionally** — `features/tasks/TaskRow.tsx:522` (`{...swipe.handlers}`), hook at `:113-165`. No viewport gate, no `e.pointerType` check, no button filter. Four distinct failure mechanisms fall out:

| # | Mechanism | Why it bites |
|---|---|---|
| a | Any left-button drag ≥8px horizontal swipes the row on desktop | `DRAG_THRESHOLD` (swipe.ts:5) is the *only* gate |
| b | **Right-click arms the gesture too** — `onPointerDown` (:138) never checks `e.button` | Right-click → menu opens → moving the mouse toward the menu travels ≥8px → the row shifts sideways underneath AND `setPointerCapture` (:153) steals the pointer from the just-opened menu. This is a large part of why the **context menus** feel broken |
| c | **The row can drag with no button held.** `onPointerUp` lives on the row and capture only starts after 8px — press down, drift off the row (<8px horizontal), release elsewhere → the row never sees pointerup → `armed` stays true → the next time the cursor merely crosses the row, `onPointerMove` (:147) drags it. The move handler never bails on `e.buttons === 0`, which is the enabling defect | This is the literal "automatically goes to the drag state" feeling |
| d | Sloppy Ctrl-click drags shift rows during multi-select | Same threshold race — part of why **bulk selection** feels broken |

**Blast radius:** every `TaskRow` surface — Tasks (all six tabs), ProjectDetail's task lists (WA-8 imports the real TaskRow), PlanningBoard's rows. Today is *not* affected (its rows are local, no swipe handlers).

**Fix direction (for the punch session, not now):** handlers no-op unless `e.pointerType === 'touch'` (the honest gate — the design ties the gesture to the device, not the width); additionally filter `e.button !== 0`, bail `onPointerMove` when `(e.buttons & 1) === 0`, and settle on `lostpointercapture`/`onPointerLeave` so an escaped pointer can't leave the row armed.

## J-2 · 🔴 Both bulk bars sit on top of the phone tab bar

`components/BulkBar.tsx:41-45` and `features/inbox/InboxBulkBar.tsx:53-57` are `position: fixed; bottom: 16; zIndex: 900`. The mobile tab bar is ~64px at z 40 — so on a phone, starting a multi-select parks the bulk bar **over** the tab bar. The toast had this exact bug and WB-3 lifted it to `74px + safe-area` at ≤767px (`ToastHost.tsx:33-39`); neither bulk bar got the same treatment.

**Fix direction:** the ToastHost pattern verbatim — a ≤767px media rule lifting `bottom` clear of the bar + `env(safe-area-inset-bottom)`.

## J-3 · 🟡 Right-click SELECTS the row, so a lone right-click can summon the bulk bar

`TaskRow.tsx:210-214` — `openMenu` runs `if (!selected) onToggleSelect?.()` before opening the menu. On Today the BulkBar mounts at `selected.size > 0`, so right-clicking a single row opens the context menu **and** pops the bulk bar behind it (then Esc closes the *selection* first per stack order, not the menu the user sees — double disorientation). Combined with J-1b's row-shift, this is most of "go over the right click context menus and bulk action's bar."

**Open question for Kai, not a unilateral fix:** is select-on-right-click wanted at all (Windows-Explorer style), or should right-click only open the menu? If kept, the bar should probably not appear for a single implicit selection.

## J-4 · 🟡 Same pointer-handler family, smaller doses

- **Calendar rail-resize divider** (`CalendarPage.tssx:311` + `:474`): no `e.button` filter — a right-button drag resizes the rail. Same one-line filter as J-1's.
- **ContextMenu closes on ANY scroll anywhere** (`components/ContextMenu.tsx:47`, capture-phase listener) — including a scroll *inside* a tall submenu, which closes the whole menu mid-aim. Intended for "menu detaches from scrolled row", but the net is too wide.
- **ContextMenu bottom clamp is estimate-based** (`:89-92`, hardcoded `itemHeight = 34`) — a menu with submenu hint rows near the viewport bottom can still overflow by a few px. LOW.
